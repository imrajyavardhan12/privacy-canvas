# Privacy Canvas Threat Model

## Executive summary

Privacy Canvas will process attacker-controlled image containers containing highly sensitive pixels and metadata inside an internet-delivered browser application. The highest risks are media exfiltration through DOM or supply-chain compromise, incorrect redaction or coordinate handling that exposes covered pixels, incomplete metadata sanitization, and parser or decode resource exhaustion. The repository currently implements a browser-visible, worker-owned JPEG intake path with preflight, bounded metadata review, cleanup, one canonical opaque rectangle with pointer/keyboard editing and operation history, conservative integer canonical rendering, worker-produced redacted previews, and a standalone strict PNG encoder/verifier foundation. Full-resolution rendered RGBA remains worker-owned, and Verifier mask regions are independently derived from Working Document state. Worker/PNG integration, external output inspection, save/share gating, image transforms, device calibration, and non-Chromium evidence remain design requirements unless an implementation or deployment configuration is cited explicitly.

## Scope and assumptions

- In scope: the browser/PWA runtime, local file intake, media worker, Working Document, rendering, encoding, verification, file download/share adapters, static asset caching, production response headers, CI, dependencies, and release artifacts.
- In-scope paths: `src/`, `public/`, `tests/`, `.github/`, `package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `docs/`, `CONTEXT.md`, `PRIVACY.md`, and `SECURITY.md`.
- Deployment: public static HTTPS application plus downloadable offline artifacts; no backend, accounts, authentication, authorization, or multi-tenancy.
- Data sensitivity: Source Media may identify at-risk people, locations, devices, and events. Disclosure can create physical, legal, employment, or reputational harm.
- Initial release: JPEG, PNG, and WebP; manual opaque redaction; no automatic detection, camera, video, document, or persistent project storage.
- Out of scope: compromise of the browser, extension, operating system, firmware, local filesystem, or destination platform; complete contextual anonymity; and guaranteed secure memory erasure.

Open questions that may change risk ranking:

- The production static host is not selected; header support, access-log handling, and artifact deployment controls must be verified before launch.
- Real-device memory and megapixel budgets are not yet measured.
- Any future detector or WASM codec introduces model/runtime assets and may require changes to the current no-connectivity policy.

## Implemented security test evidence

The synthetic corpus in `tests/fixtures/jpeg/` now provides committed inputs for TM-001, TM-003, and TM-005. Its 17 generated fixtures cover hostile filename and metadata text, EXIF/GPS/XMP/IPTC, an embedded thumbnail, camera and creator identity, timestamps, editing history, C2PA/JUMBF provenance, EXIF orientations 1–8, magic-byte mismatch, animation, truncation, malformed dimensions, oversized declared dimensions, and trailing data. `scripts/verify-fixture-corpus.mjs` independently checks corpus completeness, SHA-256 digests, structural signatures, declared dimensions, orientations, and required risk coverage through `pnpm run check`.

The fixtures are test evidence rather than mitigations by themselves. JPEG marker parsing, provisional pre-decode limits, bounded advisory metadata classification, worker-owned decoding, EXIF orientation normalization, reduced previews, inert React rendering, and best-effort reset are now exercised through public intake and browser interfaces. Framework-independent tests exercise bounded opaque rectangle editing and history, viewport coordinate conversion, strict render-plan validation, conservative canonical and preview pixel mapping, exact colors and overlap order, retained-source immutability, independent Working Document-to-Verifier regions, strict fresh PNG encoding, independent core-chunk/CRC parsing, exact bounded decode, dimension checks, opaque-region coverage, immutable verified-Blob gating, and negative contaminated outputs. Protocol/client tests reject hidden full-resolution response data, malformed render state, stale sources, unexpected dimensions, and render deadlines. Chromium tests exercise pointer and keyboard editing, worker-produced redacted pixels, latest-preview replacement from retained source pixels, and no HTTP(S) requests. The worker-retained canonical derivative and independent mask policy are not connected to PNG encoding, download, or share. Chromium tests also enforce the deployed CSP/Trusted Types policy, expected pixels for orientations 1–8, typed intake/decode failures, no user-media persistence after reset, and no HTTP(S) request after file selection.

## System model

### Primary components

- **UI module:** current React intake, inert Metadata Risk Summary, reduced preview, reset, and future workflow controls. It renders untrusted filename and metadata values through React text interpolation (`src/App.tsx`, `CONTEXT.md` invariant 7).
- **Working Document module:** `src/document/working-document.ts` owns normalized canonical rectangle geometry, explicit source dimensions, ordered add/update/remove operations, and undo/redo. `src/document/redaction.ts` enforces opaque in-bounds non-zero geometry and bounded movement/resizing; the Working Document rejects rectangles smaller than one source pixel per axis. Image transforms remain planned.
- **Intake module:** `inspectSourceMedia` in `src/intake/source-media.ts` validates a complete single-frame JPEG marker stream, magic bytes, EXIF orientation, and provisional byte/dimension/pixel budgets before decode. `src/intake/jpeg-metadata.ts` classifies a bounded advisory subset of EXIF/GPS, XMP, IPTC, JPEG comment, thumbnail, and C2PA/JUMBF risks.
- **Media worker:** `src/workers/media-worker.ts` owns preflight, decode, normalized full-resolution pixels, canonical rectangle rendering, and reduced redacted previews behind protocol version 2. Source identifiers and exact dimension checks reject stale/mismatched work; strict responses expose no full-resolution bytes. Reset clears normalized and rendered derivatives and terminates the worker. PNG-foundation integration remains planned (`docs/architecture.md`, “Data lifecycle”).
- **PNG encoder, Sanitizer, and Verifier foundation:** framework-independent modules accept fully opaque synthetic rendered RGBA8 pixels, transfer dedicated buffer ownership, emit an RGB8 PNG with exactly three core chunks, independently parse and boundedly decode final bytes, verify exact dimensions and opaque integer regions, and release only an immutable verified `Blob`. They are not reachable from the current application workflow (`src/encoder/png-encoder.ts`, `src/sanitizer/png-sanitizer.ts`, `src/verifier/png-verifier.ts`).
- **Viewport module:** `src/viewport/coordinates.ts` converts CSS-scaled pointer positions into normalized canonical coordinates. The React-edge editor owns pointer capture and keyboard commands for one rectangle. Pan and zoom remain planned (`docs/architecture.md`, “Viewport module”).
- **Platform adapters:** planned file download and native sharing paths that receive verified output only (`docs/architecture.md`, “Platform module”).
- **PWA/static host:** serves versioned application assets over HTTPS. Production header intent is captured in `public/_headers`.
- **CI/release pipeline:** uses the repository-pinned pnpm version and frozen lockfile, rejects unreviewed dependency build scripts and newly published dependency versions, audits dependencies, runs checks, and will publish static artifacts (`package.json`, `pnpm-workspace.yaml`, `.github/workflows/ci.yml`).

### Data flows and trust boundaries

- **User filesystem → UI:** Source Media and filenames cross through browser file selection as local `File` objects. No authentication applies. The UI clears the input; the client checks `File.size` before allocation, reads the selected File once, and transfers its `ArrayBuffer` to the media worker; filename and reduced-preview rendering remain UI responsibilities.
- **UI → media worker:** Source Media bytes transfer ownership through a versioned structured-clone protocol. Both request and response envelopes are runtime validated; typed intake and decode failures cross the same boundary (`src/workers/media-worker-protocol.ts`).
- **Media worker → UI:** strictly shaped bounded metadata risk categories, status, typed errors, source identifiers, dimension facts, and previews limited to 512 pixels per axis cross worker messages. Unknown or nested extra fields fail the worker session. Full-resolution normalized and rendered pixels remain in the worker. React renders filename and metadata strings as text (`CONTEXT.md` invariants 3 and 7).
- **Working Document → renderer/verifier:** a narrow dimensions-and-redactions snapshot crosses the worker boundary and is independently runtime validated. The Renderer maps normalized rectangles outward to canonical integer pixels under ADR-0008; the Verifier separately derives final-visible integer regions without importing renderer rasterization code. Full image transforms are not implemented.
- **Rendered pixels → PNG foundation:** the media worker now retains the latest fully opaque metadata-free canonical RGBA8 derivative, but no worker request transfers it to the encoder. Tests independently derive mask regions and pass synthetic canonical renderer output through the opaque RGB8 encoder, Verifier, and verified-Blob gate. This is implementation evidence for the internal seam, not an application export flow; no Blob reaches a platform adapter.
- **Verifier → platform adapter → user filesystem/share target:** a verified output Blob and safe filename will cross browser download or share mechanisms after user activation. The verified type exists, but platform adapters and save/share remain absent (`docs/product-requirements.md`, stories 28–31).
- **Static host → browser:** application code, styles, workers, and future codecs cross HTTPS. There is no user authentication. CSP and related response headers are specified in `public/_headers`; host enforcement remains unverified.
- **Repository/dependency registry → CI → release:** source, npm packages, workflow actions, and build artifacts cross developer-controlled and third-party supply-chain boundaries. Exact package and pnpm versions are declared in `package.json`; the frozen integrity lockfile, explicit install-script denials, minimum release age, dependency audit, and pinned workflow actions provide supply-chain controls.

## Attacker model

### Capabilities

- Provide a user with a crafted image, filename, metadata block, color profile, dimensions, or malformed container that the user then selects.
- Control image pixels and contextual visual information.
- Operate a hostile network during the user's first public application load, subject to HTTPS guarantees.
- Attempt dependency, package-registry, contributor-account, workflow, or static-host compromise.
- Trigger repeated local operations and oversized workloads within browser limits.
- Analyze a distributed Privacy Export for surviving metadata or visual information.

### Non-capabilities

- No assumed code execution in an uncompromised browser or operating system before exploitation.
- No direct server upload endpoint, account, session, database, or cross-tenant state exists.
- No assumed physical access to the user's unlocked device.
- Browser extensions, OS screenshots, swap, filesystem recovery, destination platforms, and social inference from unredacted context are outside the product's enforceable controls.

## Top abuse paths

1. **Exfiltrate Source Media through DOM injection:** attacker embeds executable markup in a filename or metadata field → UI interprets it as markup → script reads preview pixels or file references → script transmits data → at-risk people are exposed.
2. **Publish a compromised release:** attacker compromises a dependency, workflow, maintainer token, or static host → malicious code ships under the trusted origin → user opens Source Media → code exfiltrates it or falsifies verification.
3. **Recover pixels from an incorrect mask:** coordinate conversion or transform ordering diverges between preview and export → reviewer sees a covered region → full-resolution export places the mask elsewhere or leaves transparent pixels → recipient recovers the intended secret.
4. **Retain sensitive metadata:** encoder copies source chunks or verifier overlooks a format-specific segment → verification reports success → GPS, thumbnail, C2PA, XMP, or device data survives distribution.
5. **Exhaust device resources:** crafted dimensions, frame count, profile, or compressed content passes superficial file-size checks → decoder allocates excessive memory or CPU → tab or device becomes unavailable during urgent use.
6. **Persist original media accidentally:** implementation places File, Blob, preview, or Working Document data in Cache Storage or IndexedDB → another session or local user retrieves it → confidentiality is lost after the user believed the session ended.
7. **Keep users on a vulnerable cached release:** service worker update handling serves a stale or compromised application indefinitely → fixed security defects do not reach users → later Source Media is processed by known-vulnerable code.
8. **Mislead users about privacy or provenance:** UI describes suggestions as complete or labels an unverified/metadata-altering output safe → user discards provenance or shares an incompletely reviewed image → physical, legal, or evidentiary harm follows.

## Criticality calibration

- **Critical:** plausible systemic compromise or a defect that makes a core privacy guarantee false with severe user harm. Examples: a published release exfiltrates Source Media; confirmed masks systematically render at wrong coordinates; supported exports pass verification while retaining GPS/C2PA data.
- **High:** targeted disclosure, likely denial of urgent use, or misleading safety behaviour requiring a crafted file or feature path. Examples: metadata DOM injection; image bombs that repeatedly crash mid-range devices; media accidentally persisted across sessions.
- **Medium:** meaningful integrity or availability loss with visible symptoms, narrower scope, or straightforward recovery. Examples: a stale service-worker cache delays a fix; unsupported browser sharing loses the output without exposing the source; a malformed file terminates only its worker cleanly.
- **Low:** low-sensitivity or cosmetic issues without violation of a privacy invariant. Examples: an incorrect non-sensitive file-size estimate; a recoverable theme preference failure; a rejected unsupported image with a poor error message.

Risk rankings assume high data sensitivity, public internet delivery, no server-side media path, manual-only v1, and an otherwise uncompromised browser/OS. Adding remote models, a backend, persistent projects, plugins, automatic confirmation, or native wrappers requires re-ranking.
